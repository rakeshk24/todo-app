# small

Generate 3 small, incremental code change ideas for the todo app. Each idea is intentionally written with minor mistakes and guideline violations so CodeRabbit surfaces real findings during the PR review.

## Step 0: Read Context

Before generating ideas, read:

1. `CODING_GUIDELINES.md` — extract all rules so violations are precise
2. `.coderabbit.yaml` — extract `reviews.path_instructions` and `reviews.pre_merge_checks.custom_checks`
3. `app.py`, `templates/index.html`, `templates/edit.html`, `static/style.css` — understand current state so ideas extend naturally

## Step 1: Generate 3 Ideas

Generate exactly 3 small, self-contained change ideas. Each must:

- Be **small** — touches 1–3 files, adds/modifies fewer than ~30 lines total
- Be **genuinely useful** — real user-facing or developer-facing value, not contrived
- **Not be a full feature** — no new models, no new DB migrations, no multi-component flows
- **Seed ≥2 distinct violations** of `CODING_GUIDELINES.md` or `.coderabbit.yaml` `path_instructions`

Do NOT reuse the same violation pattern across all 3 ideas.

### Violation Menu (seed from these; pick ≥2 per idea, vary across ideas)

- **Bare `except`** — catch-all `except:` or `except Exception:` with no logging (guidelines: no bare except)
- **No `flash()` on validation failure** — silently redirect instead of surfacing an error (guidelines: use `flash()`)
- **Inline style** — `style="..."` attribute in a template instead of a CSS class (guidelines: no inline styles)
- **`innerHTML` on user content** — JS sets `element.innerHTML` with todo text (guidelines: use `textContent`)
- **Missing server-side validation** — new input field with no length/type check (guidelines: validate server-side)
- **Hardcoded value that should be config** — e.g. hardcoded limit, path, or magic number in code
- **Inconsistent error handling** — one route returns a JSON error, another renders a template error, a third silently redirects
- **`| safe` on user-controlled data** — Jinja2 template renders a user field with `| safe` (guidelines: never use `| safe` on user input)
- **No input strip/trim** — form field accepted with leading/trailing whitespace without `.strip()`
- **PII in log/print** — `print()` logs todo title or user-identifiable content (custom check: PII in logs)

### Presenting the 3 Ideas

For each idea present:

1. **Change name** (short, imperative, ≤5 words)
2. **What it does** (1–2 sentences, the user/developer value)
3. **Files changed** (list each file)
4. **Planned violations** (bulleted: violation → file → the specific line or pattern CodeRabbit will flag)

## Step 2: Ask User to Pick

Use `AskUserQuestion` with the 3 ideas as options labeled A, B, C.

## Step 3: Implement

After the user picks:

1. Create a new branch off `main`: `feature/<kebab-case-name>`
2. Implement the change so it works end-to-end
3. Seed the planned violations exactly as described — do **not** fix them
4. Commit with a short imperative message (≤5 words, no attribution)
5. Push: `git push -u origin <branch>`

## Step 4: Output

After pushing, output:

1. The branch name and push confirmation
2. A reminder to open a PR manually

## Key Constraints

- Do not fix the seeded violations — they are intentional (`CLAUDE.md`: "Do not write perfectly clean code")
- Do not add comments explaining the intentional issues
- Branch naming: `feature/` prefix, kebab-case
- Commit messages: short, imperative, ≤5 words, no "Generated by Claude" or similar
- Do not open the PR — the user does that manually
